# ADR-0001: Foundational standards — layering, Riverpod 3, error handling, documentation

- **Status:** Accepted
- **Date:** 2026-09-21
- **Milestone:** pre-v0.1

## Context

`marketplace_app` is a greenfield Flutter project that will be grown through seven milestones rather than rewritten. It serves two purposes at once: it is a marketplace application, and it is the vehicle for learning Riverpod and architecture-level Flutter skills by an author who already has deep Bloc experience.

Four things had to be settled before any feature code existed, because retrofitting them later is expensive:

1. Which SDK version the project targets, and how it is pinned.
2. Which architecture vocabulary and layering the project follows.
3. Whether Riverpod providers are hand-written or code-generated.
4. How much documentation the project carries.

A constraint specific to this project: Riverpod 3 changed significantly from Riverpod 2, and most available learning material — and most of what an LLM assistant recalls by default — describes Riverpod 2. Standards therefore have to be written down explicitly rather than assumed.

## Decision

**1. SDK — Flutter 3.47.5, pinned via FVM.** The project pins the current stable series. FVM already manages SDKs on this machine, so the pin is expressed with `fvm use`, which writes `.fvmrc` into the repo.

**2. Architecture — Clean Architecture layers under Flutter's official component names.** Feature-first folders containing `data` / `domain` / `presentation`, with components named views, view models, repositories, services, and use-cases, and with dependencies pointing inward toward `domain`.

**3. Riverpod — code generation from day one.** Providers are declared with `@riverpod` and generated by `riverpod_generator`.

**4. Documentation — three tiers.** Dartdoc on all public APIs, `docs/concepts/` explainers per milestone, and ADRs for decisions.

**5. Error handling — exceptions translated to domain failures, surfaced as `AsyncValue.error`.** No `Either`/`dartz`.

## Alternatives considered

### Strict Clean Architecture (Uncle Bob vocabulary, use-case per operation)

Entities, a use-case class for every operation, repository interfaces in `domain`, `Either`-based results throughout. Rejected because the one-use-case-per-method rule generates large amounts of pass-through boilerplate on a solo project, and because its vocabulary has drifted away from what the Flutter ecosystem and Flutter's own documentation now use — which would make the author's experience here translate less directly to real teams.

Use-cases are still used, but introduced on demand (logic spanning repositories, genuine complexity, or reuse).

### Flutter's official architecture, unmodified

Views, view models, repositories, services, with use-cases only when complexity demands. Rejected as the sole standard because it deliberately stops short of the explicit layer boundaries the author is trying to learn — `domain` as a Flutter-free, purely testable core is a skill this project exists to build. The naming was adopted; the stricter layering was kept.

### Hand-written providers, with code generation deferred

Writing `Notifier`s and providers manually for the first milestone to make the mechanics visible, migrating to `@riverpod` later. Rejected in favour of generating from day one: code generation is what current Riverpod 3 codebases and job postings actually use, and the generated declaration is close enough to the manual one that little is hidden. The cost accepted is that `build_runner` is part of the workflow from the first commit.

### `Either` / `dartz` for error handling

Rejected. `AsyncValue` is already a sealed three-state model of loading, error, and data, and Riverpod 3 makes it exhaustively matchable. Adding `Either` on top means every widget branches twice — once on `AsyncValue`, once on `Either` — to express one outcome. Typed domain failures give the type safety that `Either` is usually adopted for, without the second model.

### FVM versus a system-wide Flutter install

FVM was already in use on this machine, and the project will become a multi-package monorepo at v0.6, where a per-repo SDK pin matters. Keeping FVM also removes a real hazard discovered while setting this up: running `flutter upgrade` against an FVM-managed SDK mutates the pinned version directory in place and corrupts it. `CLAUDE.md` bans that command for this reason.

## Consequences

**Positive**

- Architecture decisions are explicit before any code exists, so the v0.4 refactor milestone has a defined target rather than an improvised one.
- Writing down the Riverpod 3 rules protects the project from Riverpod 2 material and from assistants working off stale training data.
- The naming choice keeps the author's experience transferable to Flutter teams and to Flutter's own documentation.

**Negative**

- `build_runner` is a required part of the workflow from the first commit; forgetting to run it produces confusing analyzer errors.
- Maintaining three documentation tiers is real, ongoing work, and will slow feature delivery — accepted deliberately, since learning is the point.
- The layering is stricter than a solo marketplace app strictly needs; some boilerplate is bought purely for its teaching value.

**Revisit when**

- Riverpod 3's experimental features (mutations, offline persistence) reach stable and change the recommended patterns.
- The project splits into packages at v0.6 — module boundaries may make some `core/` decisions obsolete.
- The `domain`-has-no-Flutter-types rule starts forcing awkward duplication rather than preventing coupling.
